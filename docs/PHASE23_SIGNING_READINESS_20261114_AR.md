# تجهيز التوقيع الثابت لنسخة UAT — 14 نوفمبر 2026

أضيف مسار منفصل لتوصيل مفتاح UAT المعتمد بالبناء. الفحص السابق كان يثبت وجود أسماء الإعدادات فقط؛ لا يستورد المفتاح ولا يتحقق من مطابقته للتطبيق الناتج. التغيير الحالي في أدوات البناء والتحقق فقط، ومكونات Flutter وLaravel مطابقة للمصدر الذي اجتاز اختبارات المرحلة.

## ما ينفذه المسار

- يفك المفتاح مؤقتًا في مجلد خاص داخل عامل GitHub، ويتحقق من كلمة المرور وامتلاك المفتاح الخاص وبصمة شهادة SHA-256 المعتمدة.
- يرفض الإعداد الناقص أو المفتاح غير المطابق. عند طلب البناء بالتوقيع الثابت، غياب المفتاح يفشل البناء ولا يسمح بتوقيع debug بديل.
- يمرر كلمات المرور إلى خطوتي الاستيراد والبناء فقط. لا يكتبها في تقارير أو ملفات إعداد GitHub المشتركة، ولا يرفع المفتاح ضمن المرفقات.
- يفحص شهادة APK الناتج وحزمة UAT وإصدار Android وحماية release وتوافق 16KB ومكونات التطبيق، ثم يرفع نسخة مشفرة وتقرير تحقق عام فقط.
- يحذف المفتاح المؤقت في نهاية العمل، حتى عند فشل البناء.

## إعدادات GitHub المطلوبة عند التفعيل

| الاسم | الاستخدام |
|---|---|
| `AQER_UAT_KEYSTORE_BASE64` | ملف مفتاح UAT المعتمد بصيغة Base64 |
| `AQER_RELEASE_STORE_PASSWORD` | كلمة مرور مخزن المفتاح |
| `AQER_RELEASE_KEY_ALIAS` | اسم المفتاح داخل المخزن |
| `AQER_RELEASE_KEY_PASSWORD` | كلمة مرور المفتاح |
| `AQER_UAT_SIGNING_CERT_SHA256` | بصمة الشهادة المعتمدة، 64 خانة سداسية |

توضع هذه القيم عبر إعدادات Secrets الآمنة، ولا ترسل في المحادثة أو تحفظ في المستودع. لا يكفي إعداد `AQER_RELEASE_STORE_FILE` وحده؛ هذا المسار ينشئ المسار المؤقت بنفسه بعد التحقق.

الصيغ المدعومة JKS وPKCS12. في PKCS12 يجب أن تتساوى كلمة مرور المفتاح والمخزن؛ يرفض المستورد اختلافهما صراحة لأن بعض إصدارات Java تتجاهل كلمة مرور المفتاح المختلفة. في JKS يمكن استخدام كلمتي مرور مختلفتين وتُفحصان فعليًا.

الإعداد الاختياري السابق `AQER_UAT_GOOGLE_SERVICES_JSON_BASE64` يظل منفصلًا. غيابه يبقي عميل Firebase غير مفعّل. وجوده والتحقق من تضمينه في APK لا يثبت وصول إشعار حقيقي.

## التشغيل المحدود

ملف `.github/workflows/phase23-signed-uat.yml` يعمل على فرع `work/phase23-acceptance-20261111` فقط عند تغيير أحد ملفاته المحددة. الوضع الافتراضي اختبارات أدوات التوقيع وتقرير وجود الإعدادات بصيغة نعم/لا فقط. بناء APK يحتاج إضافة العلامة `[build-signed-uat]` إلى رسالة commit مدروس يغير أحد تلك الملفات، بعد توفير الإعدادات والتأكد من بقاء مفتاح فك تشفير التسليم متاحًا لصاحبه.

البناء يستخدم `main.dart` العادي ونفس مكونات التطبيق المعتمدة، دون محاكي أو تكرار رحلات المستخدم أو استدعاءات دخول أو تعديل بيانات. لا يتضمن نشرًا على Render أو Production أو المتاجر أو تغييرًا لـ main أو PR185.

## حدود القبول

نجاح اختبارات الاستيراد بمفاتيح مؤقتة مصطنعة يثبت سلوك أدوات التوقيع، ولا يثبت توفر مفتاح المالك أو إنشاء APK موقع به. وحتى عند إنشاء APK بتوقيع ثابت، توافق التحديث فوق نسخة الهاتف الموجودة يحتاج تطابق شهادتها واختبار تحديث فعلي. مفاتيح التوقيع المؤقتة لنسخ UAT السابقة لا تصبح متوافقة تلقائيًا.

إعداد الإشعارات الكامل ما زال يشمل عميل Firebase داخل التطبيق، إعداد إرسال صالح على الخادم، عاملًا فعليًا لمعالجة طابور push، ثم دليل وصول على الجهاز. لا توجد مساحة Render مختارة في الاتصال الحالي؛ لذلك وجود إعدادات الخادم أو العامل حاليًا غير مؤكد، ولا يوصف بأنه مفقود دون فحص.

نتائج Android السابقة وتقارير قبول البنود والرحلات تبقى كما هي. التحميل المسبق الإيجابي وFCM الفعلي والقبول على هاتف حقيقي ومتطلبات TUS المؤجلة لا تُغلق باختبارات التوقيع.

## التحقق من هذا التغيير

نجح محليًا 28 اختبارًا: 21 للاستيراد، تشمل مفاتيح JKS وPKCS12 مصطنعة حقيقية، و7 للتحقق من APK والمرفقات المشفرة. أضيف اختبار مستقل لصلاحيات المسارات الفعلية في عامل GitHub، يعمل بمفتاح مصطنع وملف بيئة معزول دون تعديل إعدادات التوقيع الحقيقية. نجح أيضًا فحص صياغة YAML وكتل Shell وPython ومراجعة مستقلة لمسار الأسرار والمرفقات. لا يُطلب بناء فعلي بالتوقيع الثابت في دفعة التجهيز الحالية؛ تضاف نتيجة GitHub Actions بعد اكتمالها.
