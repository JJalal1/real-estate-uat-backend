## رحلة الاتصال الحاكمة

المصدر الحالي يؤكد هذا التسلسل:

`property → conversation → POST /messages/threads/{thread}/external-call → تسجيل حدث الاتصال → فتح tel:`

Flutter يستدعي `MessageRepository.startExternalCall` داخل `ConversationScreen` قبل فتح تطبيق الاتصال. `MessagingController::startExternalCall` يتحقق من المشاركة وحالة العقار والمعلن، وينشئ رسالة `sys-call:` ثم إشعار `external_call_started` وحدث `messages.external_call_started` ومتابعة الدعم عبر `projectContactFollowup`.

الدليل يثبت **محاولة بدء اتصال**. لا يدعي أن المكالمة أجاب عنها المعلن أو انتهت بنجاح. يتعين إبقاء هذا المعنى أيضًا أثناء نقل الواجهة.

## شروط إقفال Gate

- commit واحد للنسخة الثالثة مع APK وSHA-256 وBUILD_INFO وCI ناجحة من ذلك commit، وليس نجاح نسخة أقدم.
- بقاء مصدر Backend وData/Domain/Auth/dependencies/runtime كما في الأصل، ومراجعة إجراءات الواجهة والمسارات التي يمكن أن تحمل منطقًا رغم كونها UI.
- نجاح الاختبارات الأصلية كلها وإضافة اختبارات تفاعلية مناسبة للواجهات المنقولة، دون تخفيف الاختبارات القديمة للحصول على نتيجة خضراء.
- تنفيذ G01–G18 عبر الأدوار: زائر، مستخدم عادي، معلن مالك/دلال/مكتب وفق حالات التوثيق الأصلية، دعم، مدير دعم، مدير المنصة؛ مع الأجهزة المتعددة حيث يلزم.
- توثيق كل بند بنتيجته وIDs السجلات المستخدمة وبيئة الاختبار دون بيانات سرية، وحل الانحرافات قبل الإقفال.
- قبول صاحب المشروع صراحة نتائج المطابقة. لا يعد إنشاء الفرع أو نجاح APK أو نظافة البصمات هذا القبول.

بعد الإقفال يقترح صاحب المشروع عناصر التنظيف، وتوضع لكل منها آثارها واختباراتها وخطة رجوع. اختيار الميزات الجديدة يأتي بعد إقفال التنظيف.

الجرد والبصمات وفحص النطاق يثبتون المصدر وما تغير. الاختبارات الآلية الحالية لا تفترض أنها تغطي كل تفاعل جديد؛ اختبار الأجهزة والمقارنة الفعلية مكملان مطلوبان. لا توجد نتائج UAT للواجهة الثالثة في هذا التجهيز لأن نقل التصميم لم يبدأ.
