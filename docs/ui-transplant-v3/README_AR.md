# تجهيز النسخة الثالثة ونقل واجهة eBroker

تاريخ التحقق: 11 أكتوبر 2026. هذه خطة تنفيذ وتجهيز للنسخة الثالثة؛ نقل الواجهات لم يبدأ.

## الحالة المؤكدة

المستودع `JJalal1/real-estate-uat-backend` أصبح **Private**. المرجع الحاكم هو commit
`dc2805c9215dcd500fc7034effa953a4c3751761`، وشجرة ملفاته
`d1b00f5013aca6229c41459f8f65e5d7c25f4a94`.

تحققنا مباشرة من أن الفروع التالية تشير إلى هذا commit نفسه:

| المرجع | الغرض |
|---|---|
| `audit/system-stabilization` | الأصل المرتبط بالبيئة الحالية؛ لا يطور عليه |
| `reference/golden-dc2805` | مرجع الرجوع إلى الأصل |
| `work/ui-transplant-v3` | النسخة الثالثة المنشأة من الأصل |

تجهيز CI والتوثيق وفحص نطاق التغييرات يقدم في فرع `work/ui-transplant-v3-setup`، بطلب مراجعة إلى `work/ui-transplant-v3`. لا يدمج في الأصل أو `main`.

يوثق `golden-source-manifest.json` بصمات Git وأحجام **657 ملفًا** من الأصل. المرجع الفعلي للفحص هو commit المثبت نفسه، وليس ملف الجرد القابل للتحرير.

**مرجع eBroker لم يكتمل رفعه.** بعد استئناف المحادثة لم نجد فرعًا محفوظًا له أو أرشيفًا في `main` أو فرع العمل. المتاح في الجلسة الحالية هو صور المحادثة فقط. ورد في ملخص التدقيق السابق أن الإصدار 1.8.0 والتطبيق 1.8.0+88؛ لا يعد ذلك تحققًا جديدًا من الحزمة. حفظها والتحقق من بصماتها ومحتوياتها يحتاج إعادة إرفاق Source ZIP في هذه الجلسة.

## القرارات الحاكمة

- موافقة Private GitHub وAI محسومة بإفادة صاحب المشروع؛ لا تعاد كشرط للتقدم.
- monetization وStaging يراجعان عند الوصول إلى مرحلتهما.
- النسخة الثالثة تبدأ من مشروعنا الأصلي؛ eBroker مرجع تصميم ومكونات مناسبة.
- لا يشغل installer الخاص بالقالب، ولا يصبح Backend أو MySQL أو Auth أو أدواره أو آليات عمله أساسًا للمشروع.
- المرحلة الأولى من الخطة الكبرى هي نقل UI/UX فقط. Auth والأدوار والصلاحيات وKYC وآليات الإعلان والدعم وقاعدة البيانات وعقود API تبقى كما في الأصل.
- الاستثناء المقبول: Home بأسلوب القالب بدل فتح الخريطة أولًا؛ تبقى الخريطة وكل المسارات والرحلات متاحة.
- لا حذف ولا إضافة Feature قبل إقفال المطابقة 1:1. ثم ينظف فقط ما يحدده صاحب المشروع، وبعد إقفال التنظيف تختار ميزات القالب واحدة واحدة.

## حماية الأصل والقالب

لا تحرك فروع الأصل أو الرجوع، ولا تستخدمها هدفًا لطلبات دمج. جميع تغييرات النسخة الثالثة تقدم إلى فرعها الخاص. فحص CI يقارن المصدر بالـcommit الثابت ويتحقق من أن فرعي الأصل والرجوع لم يتحركا.

هذه حماية بالمراجع والتدقيق وCI؛ **لا تدعي تفعيل قفل صلاحيات GitHub على الفرعين**. أدوات الاتصال المتاحة لا تتضمن تعديل branch protection أو rulesets. لا يمكن للفحص وحده منع مدير مستودع من تعديل مرجع؛ لذلك يبقى commit الثابت مرجع المقارنة النهائي، وتراجع كل حركة للفروع.

عند إرفاق الحزمة:

1. احسب SHA-256 لكل ZIP قبل الاستخراج، واحفظ الأصل كما وصل خارج Git مع شهادة الشراء ورمز التفعيل في حيازة صاحب المشروع.
2. افحص محتويات ZIP ومسارات الاستخراج قراءة فقط، ثم أنشئ نسخة استخراج للفحص منفصلة عن نسخة العمل.
3. أنشئ مرجعًا منقحًا مستقلًا في فرع `reference/ebroker-1.8.0` بعد إثبات الإصدار الفعلي. لا تضف هذا المرجع إلى `work/ui-transplant-v3` ولا تدمج شجرته فيها.
4. استبعد ملفات البيئة والمفاتيح وشهادة الشراء ورمز التفعيل والإعدادات الحساسة والمخرجات المجمعة و`node_modules` و`vendor` و`build`، وسجل سبب كل استبعاد وبصمة الملف الأصلي دون قيمه.
5. احفظ ملفات مرجع التصميم مع بيان SHA-256 وجرد ومسار تحقق. لا تعدل الملفات المشمولة في البيان. إذا تغيرت سياسة الاستبعاد، أنشئ إصدارًا مرجعيًا جديدًا ببيان مستقل.
6. تحقق من المحتوى المسترجع من GitHub ومن بصماته بعد الرفع، ثم سجل commit المرجع. Base64 وسيلة نقل وليست تشفيرًا أو حماية للأسرار. لا تحكم بأن الرفع اكتمل من نجاح إنشاء blob وحده؛ يلزم commit قابل للاسترجاع وفرع يشير إليه.

الأرشيف الأصلي غير المنقح ومرجع GitHub المنقح شيئان مختلفان؛ لا توصف النسخة المنقحة بأنها الحزمة الأصلية كاملة.

## المراحل الخمس للتلبيس

التجهيز الحالي يسبق المراحل الخمس، ولا يحسب تنفيذًا للمرحلة الأولى منها.

| المرحلة | التنفيذ | شرط إقفال الدفعة |
|---|---|---|
| 1: الأساس البصري وHome | ألوان وخطوط ومكونات مشتركة، عربية وRTL، Home الجديدة والتنقل ومساحات الأدوار | كل المسارات الأصلية متاحة، حواجز الدخول والأدوار محفوظة، وAPK من commit الدفعة مع قبول العرض |
| 2: اكتشاف العقارات | بطاقات وقوائم وخريطة وبحث وفلاتر وتفاصيل وصور ومفضلة ومقارنة وبحث محفوظ ومشاريع وفق الموجود بالأصل | بيانات وعقود API الأصلية، التصفح العام والخصوصية والمفضلة بين الأجهزة وحالات العقار غير المتاح محفوظة |
| 3: الحساب والتوثيق والإعلان | واجهات الدخول والحساب، المالك والدلال والمكتب، المسودة والمعاينة والإرسال والتصحيح والصور والمستندات | نفس الأهلية والصلاحيات ومتطلبات الوثائق وحالات الإعلان وقرار النشر، دون استعارة منطق القالب |
| 4: التواصل والمعاينات والعقود | المحادثات والإشعارات والمعاينات والاتفاقات والعقود؛ اتصال المعلن من المحادثة | المحادثة تسبق الاتصال، التسجيل والإشعار ومتابعة الدعم محفوظة، والحالات والقبول بين الأطراف كما في الأصل |
| 5: الدعم والإدارة والمطابقة | بقية الواجهات ومساحات الدعم والمدير والإدارة والخدمات الموجودة، ثم اختبار كل الأدوار والرحلات | نجاح جميع بنود `PARITY_GATE_AR.md` وفحوص CI وقبول صاحب المشروع للمطابقة على الأجهزة |

كل دفعة لها PR وcommit واضح ونتائج الاختبار وAPK وبيان ما اكتمل وما بقي. لا تمثل نجاح فحوص المصدر أو البناء قبولًا بصريًا أو إثباتًا كاملًا للمطابقة.

يعرض `presentation-inventory.json` كل ملفات العرض الموجودة في الأصل ومرحلتها المقترحة؛ بعض الملفات تحتوي منطق إجراءات داخل الواجهة، ويجب إبقاؤه ومراجعته عند نقل التصميم. جرد المسارات محفوظ أيضًا في الملف.

## GitHub وRender وSupabase في كل مرحلة

| المرحلة | GitHub | Render | Supabase |
|---|---|---|---|
| تجهيز البيئة وفحص القالب | مراجع منفصلة، بصمات، فرع تجهيز وPR؛ النسخة الثالثة من الأصل | لا نشر ولا إعدادات ولا تحريك فرع runtime | لا SQL حي ولا migrations حية ولا تغيير storage |
| التلبيس 1–5 | واجهة فقط على فروع النسخة الثالثة؛ المصدر المحمي والاختبارات القديمة ثابتان | يبقى إصدار Backend المعتمد `dc2805…`؛ لا حاجة لنشر عند تغيير UI | تبقى القاعدة والسياسات والتخزين كما هي |
| المطابقة | أدلة من commit واجهة واحد مقابل الأصل، وربط APK وCI بنتائج الأدوار والرحلات | تحقق قراءة فقط من الإصدار الجاري قبل تجربة الأجهزة | تحقق قراءة فقط من ملاءمة schema والمراجع عند الحاجة |
| التنظيف المعتمد | تغييرات محددة يوافق عليها صاحب المشروع بعد المطابقة، مع اختبارات | ينشر Backend فقط إذا تغير وبعد قبول نفس الإصدار | إن لزم DB: migration في GitHub ثم قاعدة اختبار معزولة ثم تطبيق النسخة المقبولة |
| الميزات المختارة والإصدار | كل Feature منفصلة بعقود واختبارات وموافقة؛ ثم تجهيز الإصدار | نفس Backend المقبول في GitHub؛ الإنتاج مرحلة مستقلة | كل تغيير ممثل بمigration؛ لا تعديل يدوي غير ممثل بالكود |

التجهيز الحالي لم يتصل بـRender أو Supabase ولم يتحقق من حالتهما الحية مجددًا. وصف توحيدهما على الأصل مصدره التسليم السابق. CI الجديد لا ينشر إلى أي منهما ولا يجري اختبار حمل حي؛ يطبق migrations الأصلية فقط على PostgreSQL/PostGIS مؤقت داخل GitHub Actions.

`BUILD_INFO.txt` يميز بين commit الواجهة وcommit الخادم المتوقع ويثبت endpoint Frankfurt. اختلاف commit UI عن Backend طبيعي في مرحلة UI فقط لأن ملفات Backend لم تتغير. إذا تغير Backend لاحقًا يجب نشر الإصدار المقبول نفسه وتسجيله، لا الإيحاء أن بناء APK نشر الخادم.

## الفحوص ومسار البناء

`UI Transplant V3 CI` يعمل على فروع `work/ui-transplant-v3*` وطلبات المراجعة إلى فرع النسخة الثالثة، ويحفظ workflows الأصلية كما هي:

1. فحص الأصل والمراجع ونطاق المصدر، واختبار أن الفحص يرفض تغييرات API/Auth/DB/runtime والاختبارات القديمة.
2. Laravel regression على بيئة محلية مؤقتة.
3. migrations واختبارات PostgreSQL 17/PostGIS على قاعدة مؤقتة، وليست Supabase الحية.
4. Flutter **3.27.3** مع تحقق استقلال الاعتمادات، analysis والاختبارات وcompile-time Frankfurt guard ثم APK.

كشف البناء أن `pubspec.yaml` الأصلي يعلن `url_launcher` بينما `pubspec.lock` الأصلي لا يحتويه ولا يحتوي حزم منصاته السبع. البناء الأصلي يستخدم `flutter pub get` لاستكمالها عند التشغيل. لا نعدل أيًا من الملفين في Git. يحفظ `pubspec_overrides.yaml` هنا إصدارات الحزم الثماني فقط، وتنسخ إلى مساحة بناء CI المؤقتة لتثبيت الاستكمال. يتحقق `verify_v3_dependency_lock.py` أن كل سجلات الحزم الأصلية، بما فيها checksums، وقيود Dart/Flutter بقيت كما في الأصل، وأن الإضافات هي الحزم الثماني المحددة فقط؛ ثم يطبق `--enforce-lockfile` على القفل المكتمل. يسلم القفل الفعلي للبناء وبصمته مع APK، ولا يدعى أن ملف القفل الأصلي وحده كان كافيًا للبناء. الـoverrides تخصص البناء فقط، ولا تدخل إلى مجلد التطبيق في المصدر المعتمد.

لا ترقية Flutter أو اعتماد مكتبات القالب ضمن هذا التجهيز. APK يبقى بتوقيع التطوير الأصلي ومعرّف التطبيق الأصلي؛ تجهيز توقيع المتاجر يأتي ضمن مرحلة الإصدار المستقلة.

تشغيل الفحوص من checkout كامل:

```bash
python3 scripts/check_ui_transplant_v3.py --setup --verify-reference-refs
python3 -B -m unittest discover -s scripts -p 'test_*v3*.py' -v
git diff --check dc2805c9215dcd500fc7034effa953a4c3751761
```

يستخدم `--setup` لإثبات أن التجهيز لم يعدل أي ملف أصلي. أثناء التلبيس يعمل الفحص دون هذا الخيار، ويقصر التغيير على ملفات العرض المحددة واختبارات UI الجديدة والتوثيق والتجهيز. يمنع تعديل الاختبارات القديمة؛ وإذا احتاج اختبار بصري قائم تحديثًا مشروعًا، يثبت السبب وتراجع مراجعة مستقلة قبل تغيير سياسة الحماية. حواجز الدخول وطبقات البيانات والنماذج والخادم والاعتمادات وإعدادات النشر محمية.

## نقطة الاستئناف

المتابعة الهندسية تكون من هذا الدليل وطلب مراجعة التجهيز، لا من فروع التجارب القديمة. المتبقي لحفظ القالب هو إرفاق الحزمة المصدرية في هذه الجلسة والتحقق منها ثم رفع مرجعها المنقح. اعتماد خطة التلبيس يسبق تعديل الواجهات. بعد نجاح المرحلة الخامسة وقبول المطابقة، الخطوة التالية هي **التنظيف الذي يحدده صاحب المشروع**.
