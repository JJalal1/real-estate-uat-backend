# عقار — بوابة النسخ الاحتياطي واختبار TUS على UAT

> المستند **إجراء تحقق غير منفذ**، وليس إثبات وجود نسخة احتياطية ولا نجاح بروتوكول TUS في Supabase الحي. لا تُطبّق هجرة #11 أو تُفعل راية الرفع الجديدة استنادًا لهذا المستند وحده.

## الثوابت المقاسة (23 أكتوبر 2026)
- Supabase UAT: `ipxsgxsqzthpgthwvdno`، الجدول `public.listing_image_upload_intents` غير موجود، 59 هجرة Laravel وBucket `real-estate-uat` خاص.
- PR #115 هو مكان تطوير #11، وهو Draft وغير مدموج. API يحمي التذاكر بحساب ومسودة وصورة وبصمة، وFlutter ينفذ HEAD/PATCH وراء `AQER_IMAGE_TUS_ENABLED=false` افتراضيًا.
- ليس هناك إثبات أن بيانات قاعدة UAT تم تصديرها فعليًا ولا تجربة استعادة؛ اتصال Supabase SQL لا يوفّر ملف dump، كما أن خطة Free لا تشمل النسخ اليومية التلقائية.
- نجاح canary التخزين السابق للفيديو يؤكد رفع/Range/تنزيل عادي، **ولا يثبت TUS**.

## البوابة A: نسخة آمنة قابلة للاستعادة — لا SQL-only export
1. صدّر باستخدام `supabase db dump` على جهاز/بيئة تنفيذ آمنة تدعم Docker واتصال Postgres المشفر، ومعلومات DB من مدير أسرار مصادق عليه؛ أبقِ الأسرار خارج السجلات، المحادثة، وGit.
2. احفظ roles وschema وdata في ملفات مشفرة خارج موقع الخادم، مع SHA-256 والوقت ونسخة CLI وإشارة إلى قاعدة UAT الصحيحة. تشمل مراجعة منفصلة لكائنات Storage؛ dump PostgreSQL لا يحتوي bytes الكائنات.
3. استعد النسخة على قاعدة اختبار **محلية مستقلة** في حاوية مؤقتة؛ تحقق من عدد الجداول والهجرات والقيود وفهارس مسارات الإعلانات والمستخدمين بدون تصدير بياناتهم إلى المستودع. احذف بيئة الاختبار المؤقتة بعد التحقق بأمان.
4. سجّل فقط حالة النجاح، وقت النسخة، SHA بصمة أرشيف مشفر، ومكان حفظه العام؛ لا تسجل أي بيانات مستخدم أو DSN أو مفتاح.
5. لا ترحل `2026_10_23_220000_create_listing_image_upload_intents.php` إلى UAT قبل إثبات البنود السابقة وتدقيق RLS/REVOKE.

المرجع: https://supabase.com/docs/guides/platform/backups

## البوابة B: TUS synthetic-only
1. على **UAT فقط**، خزّن ملفًا اصطناعيًا في مسار فريد `private/uat-health/tus-<uuid>.bin` داخل الـbucket الخاص، دون استخدام أي إعلان أو بيانات مستخدم.
2. أصدر توقيع upload محدودًا لنفس المسار من جهة الخادم باستخدام مفتاح التخزين المحفوظ في Render، دون تسجيل المفتاح أو التوقيع. اربط طلب TUS بخاصية `x-signature`.
3. حمّل ملفًا حجمه أكبر من 6 MiB، واقطع الاتصال بعد أول جزء ثابت، ثم استخرج موضع الاستئناف من `HEAD Upload-Offset` وأرسل فقط الأجزاء المتبقية بـ`PATCH`.
4. تأكد من المجموع و`sha256` عند تنزيل الملف إلى مساحة مؤقتة محمية، ثم احذف الملف في `finally`، وراجع `storage.objects` للتأكد من عدم بقاء ملف اصطناعي؛ أعد محاولة التنظيف عند أي فشل.
5. كرر بتوقيع خاطئ أو منتهٍ وبـ`Location` خارجي؛ المطلوب رفض آمن بلا تسريب، مع قياس أخطاء HTTP وغياب تغيير في أي إعلان حقيقي.
6. لا تفعّل `LISTING_IMAGE_RESUMABLE_ENABLED` إلا بعد اختبارات دورة الصور والمسودات والملكية والـorphan cleanup، وتوثيق قبول UAT والهاتف.

المرجع: https://supabase.com/docs/guides/storage/uploads/resumable-uploads

**لا ينفذ هذا المستند أي اختبار أو هجرة.** متابعة العمل البرمجي في PR #115 مستقلة، وProduction والفيديو المؤجل خارج النطاق.


## نتيجة تجربة UAT الحية — 23 أكتوبر 2026
- PR #117 دُمج في فرع UAT لإضافة أمر اصطناعي مستقل `uat:signed-tus-storage-probe`، وليس ميزة #11 أو هجرة قاعدتها.
- أول تشغيل على Render `dep-dbdsitom7kps73bigba0` بالعلم `UAT_IMAGE_TUS_PROBE_ON_STARTUP=true` انتهى `update_failed`، ودليل السجل: `Signed TUS creation did not return HTTP 201` ثم `Signed TUS canary cleanup failed`. **بالتالي اختبار TUS الحقيقي فاشل وليس ناجحًا.**
- أعدنا علم الاختبار إلى `false`، وكذلك `LISTING_IMAGE_RESUMABLE_ENABLED=false` و`UAT_RUN_MIGRATIONS=false`. بدأ نشر الاستعادة `dep-dbdsjct9fdbs738ha3r0`، ويحتاج التحقق من حالة `live` قبل اعتماد الاستقرار.
- فحص Supabase `storage.objects` بعد الفشل: **صفر** ملفات تحت `private/uat-health/tus-%`. هذا يؤكد عدم وجود كائن مكتمل متروك بهذا المسار، ولا يؤكد تنظيف جلسة TUS غير المكتملة.
- الإجراء التالي: افصل استثناء التنظيف عن استثناء طلب TUS الأصلي، وشخّص **كود HTTP فقط بدون body/token**، وراجع اشتراطات `TUS POST` وترويسات `x-signature` في وثائق Supabase، ثم اختبر في PR معزول قبل إعادة التشغيل مرة واحدة على UAT.
- لا تغير جداول Supabase أو تفعّل ميزة #11 أو تُنشئ تكلفة. لا يوجد backup قابل للاستعادة مثبت حتى الآن.
