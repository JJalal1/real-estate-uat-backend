- لا تعتمد على إحصائية «فهرس غير مستخدم» لتقرر الحذف، ولا على «RLS بلا policy» لتقرر سياسة عمومية؛ استخدم خطط التنفيذ وواقع الصلاحيات والحمل والتوثيق.

### د. السرعة، الشبكة اليمنية، وقابلية التوسع
- اختبر بالبيانات الواقعية **من دون بيانات أشخاص حقيقية**: أحجام قوائم وصور ومحادثات كبيرة، pagination/حدود الذاكرة وN+1، نتائج البحث والترتيب والخرائط، تحميل أول شاشة، التحديثات والتعافي. افحص EXPLAIN/ANALYZE وخطط الاستعلام عند الحاجة.
- قِس cold start وwarm requests وp50/p95/p99 ومعدل الأخطاء واستهلاك CPU/Memory والاتصالات والطلبات والبايتات قبل/بعد التعديل؛ ضع **ميزانيات أداء/أهداف SLO وحجم حمل معلنًا** بدل ادعاء «سريع جدًا» من دون أرقام. قياس الضغط يكون في بيئة معزولة وبحدود آمنة؛ لا تُرهق Render UAT أو Production.
- راعِ بطء الشبكة وفقدانها و3G/Data Saver والبيانات المحدودة، و503/429/timeouts/retries مع backoff ملائم وcancellation وcache invalidation ومؤشرات loading/empty/error، وعدم تنزيل صور خارج مجال العرض أو تكرار رفع ما رُفع بنجاح.
- قابلية النمو تعتمد على **حدود معروفة وخطة قابلة للتنفيذ** للخادم والقاعدة والتخزين والفهارس والطوابير والإشعارات ومراقبة التكلفة؛ لا تضف خدمات مدفوعة أو بنية مبالغ فيها قبل قياس وموافقة المالك.

### هـ. جودة المنتج وتجربة المستخدم
- طبق نظام واجهات متناسق (ألوان/مسافات/خطوط/أيقونات/أزرار/رسائل/حالات التحميل) عبر جميع الشاشات والأدوار، مع RTL عربي صحيح وحقول أرقام/هواتف/عملة/مساحة، والوضعين الفاتح والداكن، أحجام الشاشات واللوحات وإمكانية الوصول وملصقات الأزرار.
- راجع الرحلات من البداية للنهاية: استكشاف → بحث/خريطة → تفاصيل → تواصل/حفظ → إنشاء إعلان → وسائط → مراجعة → نشر → بلاغ/حظر → حذف/استعادة. ممنوع زر لا يعمل أو صفحة وهمية أو رجوع يفقد البيانات أو حالة نجاح كاذبة.
- صمّم تجربة محترمة عند بطء الشبكة وأذونات مرفوضة وروابط مكسورة وجلسة منتهية ونتائج فارغة وخادم متوقف. لا تعرض رسالة نجاح قبل تأكيدها من الخادم ولا تكشف بيانات حساب سابق بعد الانتقال لحساب آخر.

### و. سهولة الصيانة والانضباط الهندسي
- المطلوب وحدات واضحة واسماء ملفات مستقرة واختبارات قابلة لإعادة التشغيل، وdependency locks ومراجعة تراجع وظائف قديمة. لا تُعطّل اختبارًا فاشلًا ولا تُخفف assertion ولا تستخدم mocks لإثبات أن API/DB الحقيقيين جاهزان؛ mocks مفيدة لوحدات محدودة فقط.
- وثّق أسباب التصميم والقيود وواجهات API والمخططات وخطوات التشغيل، ونظّف الكود القديم الميت في نطاق الإصلاح فقط عندما يثبت عدم استخدامه. لا تُعد صياغة المشروع كله بلا سبب أو تفتح أكثر من مصدر للحقيقة.
- كل PR يجب أن يذكر الملفات، خطر التغيير، اختبارات النجاح والرفض، CI، أثره على Backend/DB/Render، طريقة التراجع وأثره على بقية الـ29.

## 4ب. بوابة قبول إصدار المتاجر — شروط GO/NO-GO الصريحة
**هذا هو خط الشيفرة النهائي المقصود للإطلاق؛ لذلك لا تساوي بين UAT ناجح وإصدار منشور أو قابل للنشر.** يجب إثبات الآتي قبل وصف التطبيق بـ«جاهز»:

1. **وظائف واعتماد:** كل 29 بندًا مكتملًا في نطاقه مع الأدلة الفردية؛ البنود #3/#11/#21 مطبقة ومعتمدة بعد البوابات، وقرار #20 موثّق؛ لا P0/P1 مفتوحة في الأمان أو البيانات أو الرحلات الأساسية. حصر P2 المتبقية وقبول مخاطرها صراحة إذا أجيز ذلك.
2. **اختبارات حقيقية مترابطة:** CI أخضر على **SHA موحد**، اختبارات Flutter وLaravel/Postgres وStorage وHTTP UAT، ورحلات Android فعلية متعددة الأدوار والأجهزة/أحجام الشاشات والشبكات، مع نتائج نجاح/فشل وروابطها. التقرير لا يتظاهر باختبار جهاز إن لم يكن متاحًا.
3. **تجهيزات إصدار Android:** إصدار release قابل لإعادة الإنتاج، إعدادات إنتاج منفصلة ومراجعة، رقم إصدار/build صحيح، AAB أو الحزمة المطلوبة للمتجر، SHA256، توقيع رسمي محفوظ آمنًا، الأيقونة والاسم والتصاريح وApp Links والتحقق من نطاقها، FCM إذا اعتُمد ومُوّل، اختبار تحديث إلزامي/اختياري وتوافق الإصدارات.
4. **المتاجر الأخرى:** إن تقرر دعم متجر أو منصة أخرى (بما فيها iOS)، فلا تعتبرها جاهزة بمجرد نجاح Android؛ اطلب البناء والتوقيع والاختبارات والسياسات الخاصة بها. لا تدع جاهزية متجر لم يُحدد ولم يُختبر.
5. **تشغيل وأمان إنتاج:** دومين وHTTPS وتكوينات وأسرار مستقلة، صلاحيات ومراقبة وإنذار وسجلات لا تتضمن أسرارًا، نسخ احتياطي واستعادة مثبتان، خطة migrations/rollback/incident response، مراجعة سياسات الخصوصية والاحتفاظ والحذف والمحتوى/الإبلاغ والمتطلبات القانونية والمتجر بقرار المالك.
6. **استعداد نمو:** مستهدفات الأداء والحمل/التكلفة معروفة، تم قياس السلوك تحتها، وُثّقت حدود Render/Supabase وخطة التوسع والإنذار وأدوات تتبع الأعطال والتعافي. **لا تدّع أن المنصة تستوعب جمهورًا كبيرًا بلا حمل مختبر أو خطة تشغيل واقعية.**
7. **موافقة إطلاق:** تقرير GO/NO-GO مستقل، لا تكتفي بنسبة الإنجاز. حتى لو أصبح GO فنيًا، **لا نشر Production أو إرسال للمتجر أو تفعيل كلفة أو تغيير مدمر دون موافقة صاحب المشروع الصريحة**.
