## من Apache إلى PostgreSQL وStorage

- Apache prefork محدود بـ`MaxRequestWorkers=12` بناء على ميزانية pool=15 واحتياطي=3 الموثقة سابقًا. يجب تأكيد الحد الفعلي قبل إضافة العمال. رفع Apache دون قياس قد ينقل الاختناق إلى DB ويزيد الذاكرة.
- الخدمة الرسمية Free وDocker في Frankfurt والنشر التلقائي OFF. في لقطة 26 أكتوبر، 20:30–21:15 UTC، أبلغت الخدمة القائمة عن CPU limit=0.15، وبلغ أعلى RSS مرصود نحو 82.6MB، وأعلى CPU للعينة 0.0363. العينات بفواصل خمس دقائق وبها فجوة وتبدل instance؛ لا تنفي تشبعًا لحظيًا. كتالوج الخطط الجديد لا يستبدل قياس الخدمة القائمة.
- feed وmarketplace يحملان علاقات الصور مسبقًا؛ الأقسام bounded بحد ستة، وnearby يستخدم الصورة الرئيسية المدمجة وفهرس PostGIS. كشف اختبار 10k نمو قراءة المستحقات مع تعدد الملاك. جُمعت القراءة مع إبقاء شروط المبالغ والحالات والاستحقاق وتفعيل القيد وإشعاره دون تغيير مالي.
- اختبار النمو عند مالك واحد و20 مالكًا أثبت خمس قراءات مستحقات في الحالتين وتسعة استعلامات إجمالًا لصفحة 20 مالكًا. اختُبرت المبالغ المدفوعة وdisputed والحجب وعدم تكرار الإشعار. بقي اختبار السقف الأصلي ≤25 قائمًا.
- الأصل خاص وحد الصور 8MiB/24MP قائم. بقيت المشتقات وETag/304 والتحميل حسب viewport والكاش المعزول بالحساب محمية باختبارات التراجع.

## أهداف SLO مقترحة للاعتماد بعد الموارد

هذه أهداف اختبار مقترحة وليست نتائج أو SLA مباعًا. قِس من منطقة محددة وعلى شبكة Android موصوفة، وافصل TLS وDB وStorage وPHP والبايتات. لا يقارن تنزيل 8MiB بزمن JSON صغير دون معيار للشبكة.

| SLI | الهدف الأولي | شرط الإثبات |
|---|---|---|
| API قراءة دافئ | p95≤1000ms، وp99≤2500ms | ≥10k طلب بمزيج ممثل على موارد مماثلة للتجاري |
| health عميق | p95≤500ms، وp99≤1000ms | اتصال DB فعلي؛ liveness السريع ليس بديلًا |
| thumb دافئ | p95≤1000ms، وp99≤2500ms | Storage فعلي؛ فصل cache و304 عن fetch و200 |
| كتابة JSON دون وسائط كبيرة | p95≤1500ms | صحة النتيجة وrevision وrollback مطلوبة مع الزمن |
| 5xx و503 عند الحمل المستهدف | أقل من0.1%؛ صفر OOM أو فساد أو تسريب | يشمل 503 المتعمد؛ حدوثه يعني تجاوز قدرة المعالجة المستهدفة |
| هامش الموارد | CPU/RSS وpool أقل من70% بصورة مستمرة | حدود تشخيص أولية تعدل بناء على الحمل المقاس |
| push والفيديو | عمر طابور وزمن تنفيذ وإعادة محاولة محددون | تثبت بعد قياس المورد؛ قبول المزود لا يعني استلام الهاتف |

## خطة إثبات تجاري آمنة

1. بعد قرار الموارد، جهز بيئة مستقلة مماثلة للتجاري في Web وPostgres وStorage والعمال، من SHA محدد وبحسابات وبيانات اصطناعية. أثبت النسخ والاستعادة أولًا. لا تشغل حمل 10k على UAT المشتركة أو Production.
2. احفظ cold start منفصلًا ثم warmup. مزيج أولي قابل للاعتماد: 30% feed/marketplace، و20% search/map، و25% details/images، و10% messages، و10% writes/media، و5% auth/review. لا ترسل OTP مدفوعًا أو إشعارات فعلية بكثافة لاختبار الحمل.
3. ابدأ بالتزامن 1 و3 و6، ثم زد تدريجيًا مع 30 دقيقة عند كل مستوى وساعتين soak عند الحمل المختار. اجمع ≥10k طلب لتقييم p99، ووزع الصور حتى 24MP و8MiB واختبر التزاحم والانقطاع والمهل وإعادة المحاولة.
4. سجل p50/p95/p99 ومعدل الأخطاء وrequests/sec والبايتات وRSS وcgroup peak وCPU واتصالات DB وانتظارها وعدد الاستعلامات وtemp IO. افصل 304 عن200 وcache hit عنfetch، والصور عن عامل الفيديو.
5. أوقف الاختبار فور OOM أو خلل سلامة، أو عند 5xx>0.5% أو p95>ضعف الهدف لدقيقتين متتاليتين أو pool>85%. هذه حدود إيقاف آمن، ولا تخفف شروط النجاح.
6. إن كان التشبع في Web CPU أو Apache أو RSS مع DB سليم، اختبر حجم Web التالي. إن كان في DB wait أو IO أو pool، حلل الاستعلام وEXPLAIN والفهرس قبل زيادة compute. وإن تأخر الطابور مع سلامة API، افصل العامل أو وسعه. احسب ميزانية الاتصالات لكل instance قبل التوسع الأفقي.
7. لا تُغلق #109 إلا بتقرير من المصدر والموارد الممثلين، واجتياز SLO المعتمدة وsoak والأخطاء والسلامة، وإثبات المراقبة والتراجع. نتائج CI المحلية وFree لا تستوفي هذا الشرط.
