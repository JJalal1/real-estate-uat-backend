# عقار — فشل حذف الوسائط الحي والإصلاح

- PR122 دُمج في `6af2630a3482c3434d66c6b36764e14554088374` بعد 17 CI success و1 installer-transport skip، ونشر Render `dep-dbek7evavr4c73b6r8fg` أصبح Live.
- رحلة v1 الحية على Supabase Storage **فشلت** عند التحقق52 `removed_original_cleaned`؛ لا تُحسب ناجحة رغم نجاح 115 حالة في PostgreSQL المعزول مع التخزين المحلي. cleanup أبطل كل الرموز وأوقف الحسابات الستة وأرشف الإعلان الاصطناعي.
- السبب: تنظيف ListingImageService يبدأ بمشتقات v1 ثم v2 ثم الأصل. عند غياب مشتق v1 أعاد مسار الحذف الفردي **HTTP400**. CloudAssetStorageService قبل404 فقط فرفع استثناءً؛ تنظيف best-effort توقف قبل v2 والأصل. بيانات Storage أثبتت بقاء الأصل الاصطناعي بلا مرجع PropertyImage. لم نقرأ صور أشخاص أو نغير grants.
- المسار الفردي موجود في مصدر Supabase الحالي؛ لا يُدّعى أنه محذوف. نستخدم عقد SDK للحذف المجمع `DELETE /object/{bucket}` مع `prefixes:[exact_object]`: المفتاح الغائب يعيد200 وقائمة فارغة. أي400/403/404/500 من bucket نفسه يفشل ولا يُعامل كحذف ناجح.
- اختبارات جديدة تعيد إنتاج غياب v1 مع أصل ومشتق v2 موجودين، وتثبت الحذف المتكرر، وبقاء حدود المسار الخاص/العام، ورفض أخطاء المزود. تغيير توقع endpoint في اختبار قديم يعكس العقد المثبت ويحافظ على تحقق المفتاح والنطاق.
- رحلة v2 لها معرف جديد، ولا تعاد v1 ولا تمحى أدلة فشلها. ينظف الكود حسابات v1 الاصطناعية المحددة بإيصالات Audit immutable والبريد الثابت فقط، عبر Storage API، مع الاحتفاظ بالحساب/الإعلان/التاريخ المؤرشف. لا SQL DELETE على storage.objects ولا بيانات أشخاص.
- cleanup v2 يزيل مراجع صور هذه الحسابات الاصطناعية وملفاتها ويثبت غياب الأصول. إعادة بدء تشغيل اختبار فاشل/غير مكتمل لا ترجع نجاحًا مزيفًا؛ لا replay، ويُعاد success فقط لدورة passed ذات cleanup صحيح.
- تضاف رحلة مراجعة البلاغ وإغلاقه وظهور قراره لصاحبه عبر HTTP. يبقى Android الحقيقي ومزود OTP غير مختبرين بهذه الأوامر.
- لا هجرة، لا تفعيل #11 أو فيديو، لا موارد مدفوعة ولا Production. نشر v2 بعد نجاح CI فقط؛ نتيجة UAT الجديدة تُسجل لاحقًا.
